# Trip Service — TripGo

Сервис поездок MVP такси: создание, получение и завершение поездки.
HTTP API по контракту `contracts/openapi/trip-service.openapi.yaml`, данные в PostgreSQL

**Лабораторная работа 1** — HTTP API, PostgreSQL, менеджер транзакций.

**Лабораторная работа 2 в работе** — слои выделены, полный набор тестов и телеметрия ещё впереди.

## Требования

- Go 1.27+
- Docker (запущенный)
- [tripgoctl](https://github.com/course-go-autumn-2026/course-infra) — локальное окружение курса
- `psql` — необязательно, для ручных проверок

## Быстрый старт

```bash
tripgoctl cluster start        # один раз на машине
tripgoctl environment start    # PostgreSQL и observability для ЛР2
tripgoctl connect              # адреса подключений и ссылки на интерфейсы
make migrate                   # накатывает миграции
make run                       # запускает сервис на :8080
```

Проверка: `curl localhost:8080/health` → `{"status":"ok"}`.

## API

| Метод | Путь | Ответы |
|---|---|---|
| POST | `/api/v1/trips` | 201, 200 (повтор с тем же `Idempotency-Key`), 400, 409 (`driver_busy`, `idempotency_conflict`), 500 |
| GET | `/api/v1/trips/{tripId}` | 200, 400, 404, 500 |
| POST | `/api/v1/trips/{tripId}/finish` | 200, 400, 404, 409 (`trip_completed`), 500 |
| GET | `/health` | 200 |
| GET | `/ready` | 200, 503 |

Ошибки — RFC 9457, `application/problem+json`, машиночитаемый код в поле `code`.

## Как проверить

```bash
# создание
curl -si -X POST localhost:8080/api/v1/trips -H 'content-type: application/json' -d @trip.json

# 20 одновременных созданий на одного водителя — ровно один 201
seq 20 | xargs -P20 -I{} curl -s -o /dev/null -w '%{http_code}\n' \
  -X POST localhost:8080/api/v1/trips -H 'content-type: application/json' \
  -d @trip.json | sort | uniq -c
```

Для повторного запуска гонки замените `driver_id` в `trip.json` на новый UUID.

```text
internal/container/               создание и связывание реализаций
internal/domain/trip/             модель, Validate, Finish и доменные ошибки
internal/usecase/trip/create/      создание и идемпотентность
internal/usecase/trip/get/         получение поездки
internal/usecase/trip/finish/      завершение в транзакции
internal/http/                    адаптер OpenAPI, роутер, health и readiness
internal/http/trip/create/        хендлер создания и разбор JSON
internal/http/trip/get/           хендлер получения
internal/http/trip/finish/        хендлер завершения
internal/http/trip/convert/       преобразование поездки в API
internal/http/response/           запись JSON и Problem, логирование ошибок
internal/http/domainerror/        маппинг доменной ошибки в Problem
internal/repository/trip/         SQL-запросы и преобразование строк БД
internal/infra/postgres/          настройка пула соединений
internal/infra/postgres/transaction/ менеджер транзакций
internal/generated/              код, сгенерированный по OpenAPI
migrations/                      миграции goose
contracts/                       контракты курса
```

HTTP-хендлер вызывает usecase через интерфейс из своего `contract.go`.
Usecase использует доменную модель и интерфейсы репозитория и менеджера
транзакций, объявленные в его собственном `contract.go`. Интерфейсы содержат
операции, нужные конкретному потребителю. Репозиторий получает исполнителя
SQL через свой интерфейс `executorProvider`.

`container.New(ctx, cfg)` создаёт пул, менеджер транзакций, репозиторий,
usecase, логгер, объект ответов, хендлеры и HTTP-сервер. `main` управляет
запуском и остановкой. После остановки HTTP-сервера `Container.Close`
закрывает пул. Для /ready HTTP получает интерфейс с методом `Ping`.

Зависимости направлены к доменным правилам. Домен использует стандартную
библиотеку и UUID. Usecase получает внешние зависимости через конструкторы.
Правила `depguard` запрещают зависимости домена и usecase от транспорта и
конкретной инфраструктуры, а HTTP — от репозитория и драйвера PostgreSQL.

Доменная `Trip` служит общей моделью между слоями. Такая раскладка сокращает
число преобразований при трёх операциях сервиса. Общий
`http/trip/convert.ToAPI` формирует одинаковый ответ для всех трёх хендлеров.
Репозиторий сгруппирован по сущности поездки. Эти решения адаптируют раскладку
из задания к текущему размеру сервиса.

Usecase создания вызывает `Trip.Validate` до транзакции. HTTP проверяет
наличие полей и формат JSON. Usecase завершения читает поездку, вызывает
`Trip.Finish`, выполняет условный UPDATE и записывает историю в одной
транзакции. Условие по активному статусу сохраняет защиту от гонки.

Неизвестная ошибка превращается в `500 internal_error` с безопасным текстом.
Исходная ошибка записывается в лог. `ValidationError` хранит имя поля и
причину отказа, а маппер возвращает для неё `400 invalid_request`.

## Docker (задание со звёздочкой)

Многостадийная сборка, `deploy/Dockerfile`:

- стадия `build` на `golang:1.27-alpine`: скачивает модули и собирает статический бинарь (`CGO_ENABLED=0`);
- итоговый образ на `gcr.io/distroless/static-debian12:nonroot`: только бинарь `/trip-service`, без shell, исходников, Go toolchain и кеша сборки;

**Размер итогового образа — 20.7 MB** (`docker images`, колонка `DISK USAGE`; в сжатом виде 4.6 MB, из них бинарь 10.7 MB).

## Решения

### Менеджер транзакций

`transaction.TxManager` реализует `Do(ctx, fn func(ctx) error) error`.

- `Do` открывает транзакцию, кладёт её в `context` под неэкспортируемым ключом и вызывает `fn` с этим контекстом.
- Репозиторий получает исполнителя через `Executor(ctx)`: транзакция в контексте есть — работает через неё, нет — через пул. Транзакция не передаётся аргументом методов репозитория. И `pgx.Tx`, и `*pgxpool.Pool` удовлетворяют общему интерфейсу `Executor`.
- `fn` вернула `nil` → `COMMIT`; вернула ошибку → `ROLLBACK` и возврат ошибки; паника → `ROLLBACK` и повторная паника (её ловит middleware и отвечает 500).
- Вложенный `Do` находит транзакцию в контексте и не открывает новую; решение о коммите принимает внешний `Do`.
- Получение соединения + `BEGIN`, `COMMIT` и `ROLLBACK` ограничены `DATABASE_QUERY_TIMEOUT`. Откат выполняется, даже если контекст запроса отменён (клиент отключился), но не дольше этого таймаута.
- Usecase зависит от интерфейса `txManager` с одним методом `Do` и не знает про pgx.

Создание поездки — один `Do`: `INSERT` в `trips` и `INSERT` в `trip_status_history`. Проверено: при падении второй вставки в `trips` ничего не остаётся. Завершение — тоже один `Do`: `UPDATE` и запись в журнал.

### Уровень изоляции: Read Committed

Уровень по умолчанию в PostgreSQL. Инварианты держит не изоляция, а механизмы, корректно работающие на Read Committed:

- «одна активная поездка на водителя» — уникальный индекс;
- «нельзя завершить дважды» — условный `UPDATE` (блокировка строки и перепроверка условия).

Serializable дал бы тот же результат, но под конкурентной нагрузкой возвращал бы ошибки сериализации (`40001`), требующие повторов. Выгоды для наших сценариев нет.

### Запрет двух активных поездок у водителя

Частичный уникальный индекс в миграции `00001`:

```sql
CREATE UNIQUE INDEX trips_driver_active_uniq ON trips (driver_id) WHERE status = 'active';
```

Уникальность проверяет база в момент вставки, поэтому правило держится при одновременных запросах: второй `INSERT` ждёт завершения первой транзакции и получает `23505`. Репозиторий распознаёт `23505` по коду и имени ограничения и возвращает доменную `ErrDriverBusy`  `409 driver_busy`. Проверка `SELECT` перед `INSERT` не использована: два параллельных запроса оба прошли бы её раньше, чем любой вставит строку. Индекс частичный, чтобы не ограничивать число завершённых поездок.

Проверено: 20 одновременных запросов на одного водителя один 201 и девятнадцать 409.

### Защита завершения от гонки

```sql
UPDATE trips SET status = 'completed', finished_at = $1, updated_at = now()
WHERE id = $2 AND status = 'active'
RETURNING ...
```

Проверка статуса и запись — одна операция. Второй параллельный `UPDATE` ждёт блокировку строки, после коммита первого перепроверяет условие на актуальной версии строки и ничего не обновляет. `finished_at` не перезаписывается, запись в журнале одна. До UPDATE usecase читает поездку и проверяет доменное правило. Отсутствующая поездка даёт 404, завершённая — 409. Ноль обновлённых строк после успешной проверки означает, что параллельный запрос успел завершить поездку, и также даёт 409.

Проверено: 20 одновременных `finish` одной поездки → один 200 и девятнадцать 409.

### Валидация запроса на создание

Сгенерированные поля обязательных свойств — не указатели, поэтому отсутствие поля неотличимо от нулевого значения. Валидация в три этапа:

1. наличие обязательных ключей (включая `latitude`/`longitude` внутри точек) по сырому JSON;
2. строгий разбор с `DisallowUnknownFields` (`additionalProperties: false`) и отказом от данных после объекта;
3. `Trip.Validate` в домене проверяет непустые UUID, координаты и `price >= 0`.

Диапазоны координат и неотрицательная цена дополнительно защищены `CHECK` в схеме.

### Идемпотентность создания поездки (задание со звёздочкой)

`POST /api/v1/trips` принимает необязательный заголовок `Idempotency-Key` (UUID, генерирует клиент).

| Запрос | Ответ |
|---|---|
| первый с этим ключом | `201`, поездка создана |
| тот же ключ и то же тело | `200` и та же поездка, вторая не создаётся |
| тот же ключ, другое тело | `409 idempotency_conflict` |
| без заголовка | как обычно, `201` |

**Где хранится ключ.** Таблица `idempotency_keys` (миграция `00003`): ключ, SHA-256 тела запроса, `trip_id`, `created_at`. Ключ пишется в той же транзакции, что поездка и журнал: если создание не удалось (например, `driver_busy`), ключ не сохраняется и повтор обработается заново.

**Как отличаем повтор от конфликта.** По SHA-256 от уже разобранных полей запроса (`user_id`, `driver_id`, координаты, `price`), а не от сырого JSON: пробелы, порядок полей и регистр UUID на результат не влияют.

**Конкурентные запросы.** Первым действием в транзакции ключ «занимается» через `INSERT … ON CONFLICT (key)`. Второй запрос с тем же ключом ждёт на первичном ключе, пока первая транзакция завершится, и дальше видит готовую запись: отдаёт ту же поездку или `409`. Две поездки по одному ключу невозможны. `ON CONFLICT` не превращает конфликт в ошибку, поэтому транзакция остаётся живой и в ней можно прочитать существующий ключ. Внешний ключ `trip_id - trips` объявлен `DEFERRABLE INITIALLY DEFERRED`: ключ вставляется раньше поездки, проверка откладывается до `COMMIT`.

**Срок жизни ключа 24 часа** (`IDEMPOTENCY_KEY_TTL`). Ключ старше срока считается свободным: тот же `INSERT … ON CONFLICT DO UPDATE … WHERE created_at < now() - TTL` перезаписывает его под новую поездку.

Проверено: 20 одновременных запросов с одним ключом и одним телом один `201` и девятнадцать `200`, одна поездка.

### Прочее

- `/health` не ходит в базу: при недоступной базе процесс жив, перезапуск не поможет. `/ready` пингует базу и отвечает 503 - оркестратор перестаёт слать трафик, но не перезапускает.
- `finished_at` и `last_position_at` в ответе необязательные: у активной поездки поле `finished_at` отсутствует в JSON (сгенерированный тег `omitempty`).
- `started_at` и `finished_at` выставляет сервис в UTC с точностью до микросекунд — как хранит PostgreSQL.
- Паника в хендлере логируется со стеком и превращается в `500 internal_error` в `problem+json`.
